AI OS Architecture

A personal command center — job search CRM, AI assistant, knowledge base, finances, and business OS — deployed as a single FastAPI monorepo on a $4.50/mo Hetzner VPS. This document explains not just what each component does, but why it was chosen and how it actually works under the hood.

Big Picture

One Docker image. Two domains. One FastAPI app handling everything — database, AI agent, static file serving, background workers, and webhooks. The entire system runs on a $4.50/mo VPS with 2 vCPUs and 4GB RAM.

User's browser │ HTTPS (TLS terminated here) Caddy — runs on HOST (not Docker), handles TLS + basicauth │ HTTP → localhost:4116 FastAPI :4116 ← one port serves both domains ├── /api/* → Python async route handlers ├── /webhooks/* → Fathom meeting recordings └── /* → React SPA (index.html) — client-side routing FastAPI talks to: Postgres (pgvector:pg16) — two databases: jobsearch + daily_log Redis — Celery broker + result backend SQLite — okf.db (proposals) + sessions.db (chat history) Background tasks (separate containers, same image): celery-worker — scrapers, embeddings, proposal generation celery-beat — cron scheduler (8am scrapes, Sunday backfill) External APIs: DeepSeek — Ima's LLM (~10× cheaper than GPT-4, OpenAI-compatible protocol) OpenAI — text-embedding-3-small (semantic search vectors) Langfuse — LLM observability (traces every Ima conversation) PandaDoc — proposal PDF generation Fathom — meeting recordings (webhooks → vault markdown notes)

One repo, two personalities. home.dmytropetryshchuk.com = personal light theme. onekeyflow.com = agency dark theme. The distinction is made in the browser: IS_OKF = hostname.includes('onekeyflow') applies the dark class to <html>. Both domains share the same backend, database, and Ima instance — no duplication.

Why a monorepo instead of microservices?

Microservices trade operational simplicity for scale. At this scope — one developer, one server — microservices would mean 5× the deployment complexity with zero benefit. A monorepo means one deploy pipeline, one place to look when something breaks, and no network overhead between "services." The modularity comes from routers and Celery queues, not separate processes.

Request Lifecycle

Tracing a request end-to-end is the best way to understand how all the layers connect.

Synchronous request (Add a company to the CRM)

1. Browser sends POST /api/jobsearch/companies {"name": "Acme Corp", "website": "acme.com"} 2. Caddy checks HTTP Basic Auth header TLS is terminated here → plain HTTP to localhost:4116 3. FastAPI matches the route in routers/jobsearch.py Pydantic validates the request body against CompanyCreate schema Invalid field types → 422 Unprocessable Entity (before handler runs) 4. Dependency injection: FastAPI calls db.get_jobsearch_pool() Returns the module-level pool object (pre-created at startup) 5. Handler runs: await pool.execute("INSERT INTO companies VALUES ($1, $2)", name, website) asyncpg sends SQL over a pooled TCP connection to Postgres Raw SQL, parameterized — no ORM, no SQL injection possible 6. Returns {"ok": true, "id": "abc123"} FastAPI serializes via Pydantic, sets Content-Type: application/json

Async trigger request (Run a job scrape)

1. Browser sends POST /api/jobsearch/trigger/scrape.sd 2. Handler validates task_type in allowed_types set Calls events.emit(pool, "ui", task_type, {}) → inserts os_events {type: "scrape.sd", status: "pending"} + process_event.delay(event_id) Celery serializes to JSON → pushes to "celery" list in Redis Returns immediately — {"ok": true} — does not wait for scrape to finish 3. celery-worker container polls Redis (BRPOP — blocking pop) Gets the task, deserializes, calls process_event(event_id) Loads os_events row, marks status "processing" Dispatches to scraper by event.type 4. Scraper runs, fetches jobs, upserts into job_postings Marks event status "done" (or "failed" with error text)

The os_events table is your audit trail. Every background operation — scrapes, embeds, proposal generation — flows through this table. You can always answer "did that thing run? when? did it succeed?" by querying os_events. This is a pattern called the outbox pattern — writes to the DB are the source of truth, not in-memory state.

Why not two separate deployments?

Two deployments = two servers, two CI pipelines, two Postgres instances, potentially diverging codebases. Here, both "products" share 95% of the same code, data, and Ima instance. The only difference is which nav items show. One codebase is strictly easier to maintain. If the agency grows, you split it out then — not before you need to.

FastAPI

What is FastAPI?

FastAPI is a Python web framework — software that turns Python functions into HTTP endpoints. You write a function, decorate it with @router.get("/path"), and FastAPI handles routing, request parsing, response serialization, and documentation generation. The "Fast" in FastAPI refers to two things: speed of development (Pydantic + auto-docs) and speed of execution (async I/O).

Why FastAPI over the alternatives

vs Django

Django is "batteries included" — ORM, admin, auth, templates baked in. Great for classic web apps. But it's synchronous by default, heavy, and its ORM adds abstraction overhead. We don't need templates or admin — we have a React SPA. Django's sync model would block a thread per DB call.

vs Flask

Flask is minimal — just routing and request handling. You add everything else. Like Django, it's synchronous by default. No built-in validation. For an async API with structured data, you'd end up reinventing what FastAPI gives you for free.

vs Express (Node)

Node is natively async but the Python AI/ML ecosystem is vastly richer. LiteLLM, asyncpg, Celery, Alembic — all Python-first. Mixing languages adds cognitive overhead with no benefit at this scale.

FastAPI wins because

Async-first (handles I/O without blocking threads), Pydantic validation on every request body (auto 422 on bad data), automatic OpenAPI docs at /docs, and it's the fastest pure-Python framework on benchmarks.

Entry point: aios/main.py

The app has a lifespan — code that runs once on startup and once on shutdown. This is where connection pools are initialized. The @asynccontextmanager pattern means "run this code when starting, yield (serve requests), then run cleanup when stopping":

main.py@asynccontextmanager
async def lifespan(app: FastAPI):
    _configure_litellm()           # wire Langfuse callbacks (one-time setup)
    await db.init_jobsearch_pool() # create asyncpg pool — 10 warm connections
    await db.init_daily_log_pool()
    yield                          # ← app runs here, serving requests
    await db.close_jobsearch_pool()
    await db.close_daily_log_pool()

Pydantic: validation for free

Every request body is declared as a Pydantic model. FastAPI reads the incoming JSON, runs Pydantic's validation, and either calls your handler or returns a 422 with specific field errors — before your code runs:

class CompanyCreate(BaseModel):
    name: str                    # required, must be string
    website: str | None = None   # optional
    stage: Literal["active", "dropped"] = "active"  # enum — invalid value → 422

@router.post("/companies")
async def create_company(
    body: CompanyCreate,                           # auto-validated
    pool: asyncpg.Pool = Depends(db.get_jobsearch_pool)  # injected
):
    await pool.execute("INSERT INTO companies (name, website) VALUES ($1, $2)",
                       body.name, body.website)
    return {"ok": True}

Dependency Injection. Depends() is FastAPI's way of running setup code before a handler. get_jobsearch_pool() returns the module-level pool reference — it's called on every request but creating a new connection is not. The pool maintains pre-opened connections and loans them out per request.

SPA fallback — how the React app works

React Router handles navigation client-side. Every URL like /jobsearch/leads doesn't correspond to a file on disk — React renders it. The catch-all route makes this work:

@app.get("/{full_path:path}")
async def spa(full_path: str) -> FileResponse:
    candidate = _PUBLIC / full_path
    if candidate.is_file():
        return FileResponse(candidate)   # serve JS/CSS/images directly
    return FileResponse(_PUBLIC / "index.html")  # everything else → SPA

Async Python — How It Actually Works

The core mental model

Async Python is cooperative multitasking, not true parallelism. There's one thread running one task at a time. But when a task says "I'm waiting for the database to respond" (await), the event loop switches to another task instead of sitting idle. When the DB responds, the first task resumes. No threads, no locking, no race conditions.

Sync vs Async — what changes

Synchronous (Flask/Django default): Request 1: handler starts, calls DB, BLOCKS thread waiting for response Request 2: waits in queue (thread is occupied) ... DB responds to Request 1 → thread resumes Request 2 can now start One thread = one request at a time. Need more concurrency = more threads. 10 concurrent requests = 10 threads sitting idle waiting for DB. Async (FastAPI/asyncio): Request 1: handler starts, calls await pool.fetchrow() event loop: "ok, you're waiting" → starts Request 2 Request 2: handler starts, calls await pool.fetchrow() event loop: "ok, you're waiting" → starts Request 3 ... DB responds to Request 1 → event loop resumes Request 1 handler DB responds to Request 2 → event loop resumes Request 2 handler One thread handles many requests because most web server time is spent waiting for I/O (DB, network) not computing.

The trap: blocking in async code. If you call a sync function inside an async handler — like requests.get(url) (sync HTTP) or time.sleep() — you block the entire event loop and no other requests can run. Always use async alternatives: aiohttp, asyncio.sleep(). Celery tasks use sync code because they run in separate processes.

Why Celery workers are separate processes

Celery workers use synchronous Python. You can't use asyncio in Celery tasks without significant complexity. Rather than fighting this, the workers run as entirely separate containers — they have no shared memory with FastAPI and communicate only through Redis (task queue) and Postgres (data). This is actually cleaner: async I/O for the web server, sync for the workers.

Database Layer

Two Postgres databases — why not one?

Job search and daily log data are conceptually independent. Separate databases mean: independent backup/restore, clear ownership of schemas, and the jobsearch DB can grow large (pgvector stores 1536-float vectors) without affecting the lightweight habit tracker. Both run in the same Postgres container — it's the logical separation that matters, not a second server.

Connection pools — the taxi rank analogy

Why not open a connection per request?

Opening a Postgres connection involves a TCP handshake, TLS negotiation (if enabled), Postgres authentication, and session setup — typically 5–20ms. At 100 req/s that's 1–2 seconds of pure connection overhead. A pool pre-opens N connections at startup and loans them to handlers. Getting a connection from the pool is ~microseconds. Think of it as a taxi rank where cabs wait for passengers — vs calling a cab company each time and waiting for one to drive over.

# db.py — pool created ONCE at startup
_jobsearch_pool = await asyncpg.create_pool(
    settings.jobsearch_database_url,
    min_size=10,  # always 10 warm connections ready
    max_size=20   # can burst to 20 under load
)

# In any handler — microseconds to get a connection
async with pool.acquire() as conn:
    row = await conn.fetchrow("SELECT * FROM companies WHERE id = $1", company_id)
# connection automatically returned to pool

Two connection flavors. FastAPI routes use asyncpg (pure async, fastest Python Postgres driver). Celery workers use psycopg2 via SQLAlchemy (sync) — Celery runs in separate processes that can't use asyncio. The SyncSession in db.py wraps SQLAlchemy's ORM just for the os_events model used by Celery to read/write task status.

Why no ORM for the main routes?

ORMs (like SQLAlchemy's ORM or Django ORM) map Python objects to SQL. They're convenient but generate suboptimal queries, make complex joins awkward, and add a layer of abstraction that makes it harder to reason about what SQL actually runs. Raw parameterized SQL is direct, fast, and readable. The $1 parameter syntax prevents SQL injection at the driver level.

Alembic: schema migrations

Why migrations matter

You can't just change a CREATE TABLE statement when data already exists. Migrations are versioned scripts that apply changes to a live database. Alembic tracks which migrations have run in an alembic_version table. upgrade head applies all pending migrations in order. Every schema change — adding a column, creating an index, changing a type — gets its own migration file with upgrade() and downgrade() functions. This means you can roll back a schema change, and different environments (dev, prod) can always catch up to "head" reliably.

alembic -c migrations/jobsearch.ini upgrade head   # apply pending migrations
alembic -c migrations/jobsearch.ini downgrade -1  # roll back one migration

# Migration files live in: migrations/jobsearch/versions/
# Each has upgrade() and downgrade():
def upgrade():
    op.add_column('contacts', sa.Column('linkedin_url', sa.String()))

def downgrade():
    op.drop_column('contacts', 'linkedin_url')

Data-Access Seams — One Interface, Two Adapters

The problem this solves

The same database logic used to be hand-written at every call site. "Create an os_event and enqueue it" lived in two routers and a Celery task. "Embed text and upsert it" was copy-pasted four times. "Find-or-create a company / job posting" was implemented twice — once with asyncpg in the agent, once with psycopg2 in the scraper — and the two copies had drifted. When logic lives in many places, it changes in some and not others. Bugs hide in the gap.

The fix: each piece of shared data logic now lives in one module that owns the invariant. Because the app reaches Postgres through two drivers — asyncpg (FastAPI routes) and psycopg2 (Celery workers) — each module exposes one interface with two adapters: an async one for routes, a sync one for workers. They share the contract (column set, conflict key, id scheme); only the literal SQL paramstyle differs.

Why two adapters and not one driver? Celery runs in separate processes that can't share FastAPI's asyncio event loop — they genuinely need a sync driver. Two real callers across a seam means two adapters is honest, not redundant. Forcing everything onto one driver would mean either blocking the async web server or running asyncio inside Celery — both worse than a small, shared invariant with two thin adapters.

The agent tool registry

Ima's tool dispatch was a single 500-line if/elif name == … ladder with SQL inline in each branch. It's now a registry: a _TOOL_HANDLERS dict mapping each tool name to an async handler(inputs, pool). Adding a tool means registering an adapter, not editing a conditional. The CRM tools (upsert_company, upsert_job_posting) now delegate to intake.py instead of carrying their own copy of the find-or-create SQL — so the agent and the scraper can no longer drift apart.

# agent.py — dispatch is now a lookup, not a ladder
_TOOL_HANDLERS = {"upsert_company": _tool_upsert_company, ...}  # 30 tools

async def run_tool(name, inputs, pool):
    handler = _TOOL_HANDLERS.get(name)
    if handler is None:
        return json.dumps({"error": f"Unknown tool: {name}"})
    return await handler(inputs, pool)

The test surface

Tests run with pytest from aios/ and don't touch a real Postgres. tests/conftest.py provides fakes that satisfy each driver's interface: an AsyncMock asyncpg pool and a FakeConn that records SQL and serves staged results. A module's invariant is exercised by injecting a fake across its interface — for example sync_jobs_to_db(jobs, conn=…) now takes an injectable connection, so the scraper's filter chain and dedup orchestration are testable without a database. The agent registry has a coverage test that pins set(_TOOL_HANDLERS) == declared TOOLS, so a tool can never be declared without a handler.

Interview talking points
  • Duplication isn't a style problem — it's a correctness problem. Two copies of one rule drift; the bug is the divergence, not the repetition
  • A seam with two real callers earns two adapters; a seam with one caller is hypothetical — don't build it (e.g. upsert_contact stays in the agent, its only caller)
  • Depth = leverage at the interface: a lot of behaviour behind a small call. emit() hides id-generation, the INSERT, and the enqueue behind four arguments
  • The interface is the test surface — if you can inject a fake across it, the module is the right shape

pgvector + Semantic Search (RAG)

The problem with keyword search

SQL LIKE '%AI startup%' finds documents containing those exact words. But "founding ML infrastructure engineer" won't match "AI startup" even though the meaning is essentially the same. Semantic search finds documents that mean the same thing — not documents that share the same words.

What is an embedding?

An embedding is a list of 1536 numbers that represents the meaning of a piece of text. These numbers are produced by a neural network (OpenAI's text-embedding-3-small) trained to place semantically similar texts close together in this 1536-dimensional space. "senior ML engineer" and "founding AI engineer" produce number lists that are close together. "apple pie recipe" produces a number list that's far from both.

Text: "founding engineer AI startup" ↓ OpenAI text-embedding-3-small API call (~$0.02 per million tokens) Vector: [0.021, -0.048, 0.103, 0.017, -0.091, ... 1536 numbers] ↓ stored in Postgres via pgvector extension Query: "senior ML engineer" ↓ same embedding process → query vector [0.019, -0.052, 0.098, ...] ↓ SELECT id, chunk_text FROM embeddings ORDER BY embedding <=> $1 -- <=> is cosine distance (0=identical, 2=opposite) LIMIT 10 Results: the 10 semantically closest documents

Cosine similarity — the math in plain English

Cosine distance measures the angle between two vectors. Parallel vectors (angle=0, cosine=1) are identical. Perpendicular vectors (angle=90°, cosine=0) are unrelated. The distance between "AI engineer" and "ML infrastructure" is small. The distance between "AI engineer" and "pasta recipe" is large. pgvector computes this efficiently using an ivfflat index — approximate nearest-neighbor search that trades a tiny bit of accuracy for dramatically faster queries on large datasets.

RAG: Retrieval-Augmented Generation

RAG is the pattern of fetching relevant context before generating an LLM response. Instead of putting everything into the prompt (expensive, has context limits), you embed a query, retrieve the top-K relevant chunks, and add only those to the prompt. This is how Ima answers "what did I discuss with Bram?" — she embeds the question, finds the Fathom meeting note in pgvector, and uses it as context.

    vec = await embed_async(text)

Interview talking points
  • Embeddings are learned representations — the model encodes semantic meaning into geometry
  • ivfflat is approximate (inverted file) — it trades 5-10% recall for 10-100× speed on large tables
  • RAG vs fine-tuning: RAG adds fresh data at inference time, fine-tuning bakes it into weights. RAG is cheaper and updatable without retraining
  • Chunking strategy matters: we store up to 4000 chars per chunk — too small loses context, too large loses precision

Celery + Redis — Background Task Queue

Why not just run slow tasks in FastAPI handlers?

HTTP has timeouts. Scrapers run for 30-60 seconds. If you ran a scraper in a handler, the browser would timeout and show an error. More importantly, slow handlers block other requests (at least exhaust the connection pool). Background task queues decouple request handling from execution: accept the job instantly, process it when resources are available, report status via polling or webhooks.

How Celery + Redis works

Producer (FastAPI handler): process_event.delay(event_id) → serializes {"task": "process_event", "args": [event_id]} to JSON → LPUSH celery [json_payload] ← Redis command: push to left of list → returns immediately, handler responds 200 Broker (Redis): Holds a list called "celery" (the queue name) Tasks sit here until a worker picks them up Redis is in-memory → microsecond enqueue/dequeue Consumer (celery-worker container): BRPOP celery 0 ← blocking pop: wait forever for an item Gets task JSON, deserializes, calls process_event(event_id) Marks os_events row done/failed BRPOP again — waiting for next task Scheduler (celery-beat container): Reads beat_schedule dict On cron tick → inserts os_events row → enqueues process_event.delay() Like cron but integrated: retries, result tracking, same task code

Why Redis as the broker?

Celery supports several brokers: Redis, RabbitMQ, Amazon SQS. Redis is the simplest — it's a key-value store already in the stack (could also be used for caching). RabbitMQ is more feature-rich (message durability, routing, dead-letter queues) but is a heavier dependency. For this scale, Redis lists are sufficient. One caveat: Redis is in-memory, so if the server restarts before a task is picked up, that task is lost — acceptable for scrapers (they run again next day) and embeds (idempotent via UPSERT).

Two queues

The worker listens on two queues: celery (default — scrapers, embeds) and okf (proposal generation). OKF tasks call an LLM to generate proposal text — potentially 30+ seconds. Isolating them to a separate queue means a slow proposal can't delay a job scrape that someone triggered manually.

Interview talking points
  • Message queues decouple producers from consumers — the web server doesn't need to know or care how long the task takes
  • Idempotency matters: tasks should be safe to retry. Embed tasks use UPSERT (ON CONFLICT UPDATE) so re-running is harmless
  • The os_events table is the outbox pattern — write to DB first, then enqueue. If Redis is down when you push, you've lost the task. Writing to DB first means you can recover by re-enqueuing pending events

Ima — The AI Agent

What makes something an "agent" vs a chatbot?

A chatbot takes a message and returns a response — one round trip. An agent can take actions: call tools, observe results, decide what to do next, call more tools, and eventually produce a response. The model orchestrates a multi-step workflow. This is what lets Ima answer "find me jobs at AI startups that match my background" — she searches, reads results, filters, possibly searches again, then responds. A chatbot couldn't do that; an agent can.

The tool-use loop

User: "what did I discuss with Bram?" Iteration 1: LLM sees the question + list of available tools LLM decides: call semantic_search(query="Bram", source_type="vault") Tool executes → returns: Fathom meeting note "2026-05-23 - Bram call.md" Tool result appended to message history Iteration 2: LLM sees the meeting note content in context LLM decides: no more tools needed → generate response Loop exits → response streamed to browser Each iteration is a full LLM call. Tools execute in Python on the server. The LLM never "runs" the tools — it emits a JSON blob saying "call this function with these args" and we actually run it.

How tool use works at the protocol level

Tool use is not magic — it's a structured output format. You pass the LLM a list of tool schemas (JSON Schema definitions of function names and parameters). The model is trained to output a special "tool call" token sequence instead of text when it wants to invoke a tool. The inference server returns this as a structured object. You run the function, append the result to messages as a "tool result" message, and call the LLM again. The LLM has been trained on examples of this pattern so it knows how to use it.

# The "tool" from the LLM's perspective is just a JSON schema:
{
  "name": "semantic_search",
  "description": "Search vault, notes, or jobs by meaning",
  "parameters": {
    "type": "object",
    "properties": {
      "query": {"type": "string"},
      "source_type": {"enum": ["vault", "note", "job_posting"], "optional": true}
    },
    "required": ["query"]
  }
}

# LLM outputs:
{"tool_calls": [{"name": "semantic_search", "arguments": {"query": "Bram", "source_type": "vault"}}]}

# We execute it, get results, append to messages, call LLM again

Tool dispatch — a registry, not a ladder

The 30 tools dispatch through a _TOOL_HANDLERS dict (name → async handler(inputs, pool)) rather than one long if/elif chain. Each handler is independently testable, and the CRM tools delegate their find-or-create SQL to intake.py so the agent and the scraper share one deduplication invariant. LiteLLM + DeepSeek

The problem LiteLLM solves

Every LLM provider has a different API shape, authentication method, and SDK. OpenAI, Anthropic, DeepSeek, Gemini, Cohere — all different. LiteLLM is a translation layer: you write one call (litellm.acompletion(model="deepseek/deepseek-chat", ...)) and LiteLLM handles the translation to whichever provider's actual API format. Switching models is a one-line change.

The streaming call

# agent.py — the core LLM call in the agentic loop
response = await litellm.acompletion(
    model="deepseek/deepseek-chat",   # LiteLLM routes to DeepSeek's API
    messages=messages,                 # full conversation history + system prompt
    tools=TOOLS,                       # JSON schemas of all available tools
    stream=True,                       # SSE: chunks arrive as generated
)
async for chunk in response:
    # chunk.choices[0].delta can contain:
    # .content → text token (user-visible)
    # .tool_calls → the model wants to call a tool

Why DeepSeek?

Cost

DeepSeek is ~10-20× cheaper than GPT-4 Turbo per token for comparable quality on tool-use tasks. At high volume (Ima conversations multiple times daily), this matters significantly.

OpenAI-compatible protocol

DeepSeek uses the same OpenAI message format and tool-use JSON schema. Switching from OpenAI to DeepSeek required zero code changes — just changing the model string in LiteLLM.

Tool use quality

DeepSeek reliably follows tool-use protocols — it correctly emits tool calls, uses parameter schemas, and chains tools appropriately. Some cheaper models hallucinate tool calls or misformat JSON.

Streaming support

Supports streaming SSE responses, which is required for Ima's "text appears as it's generated" UX. Not all models/providers support streaming.

Langfuse — LLM Observability

Why observability matters for LLMs

Traditional server logs tell you a route was called and returned 200. That's not enough for LLM applications — you need to know: what prompt was sent, what the model responded, which tools were called and with what arguments, how many tokens were consumed, how long each step took, and whether the output was good. Langfuse captures all of this as structured traces.

Langfuse is wired up as a LiteLLM callback — one-time setup in main.py, no code changes needed anywhere else:

litellm.success_callback = ["langfuse"]
litellm.failure_callback = ["langfuse"]
# Every LiteLLM call now automatically traced

This gives you: prompt → response → tool calls → token counts → latency — all linked into a trace per conversation turn. You can see exactly what Ima "saw" and "said" on any given interaction.

Version pinning. Langfuse 3.x moved to an OpenTelemetry-based API and removed the Langfuse().trace() method that LiteLLM 1.89.3 expects. Pin: langfuse==2.60.10 — the last release with the old low-level SDK. This is a hard dependency lock; upgrading either LiteLLM or Langfuse without testing will break tracing silently.

React + Vite Frontend

What a React SPA actually is

A Single Page Application loads one HTML file and one JavaScript bundle. From there, JavaScript renders every "page" — routing, data fetching, UI — without ever asking the server for a new HTML document. The URL changes (React Router updates window.history) but no page load happens. This is why the server's catch-all route always returns index.html for non-API paths — the browser only ever needs that one HTML file.

Why Vite over Create React App?

Create React App uses Webpack — a bundler that has to bundle the entire app on every change, even in dev. Vite uses native ES modules in the browser: it only transforms the file you actually changed, plus its direct imports. Hot Module Replacement (HMR) that takes 200ms in CRA takes 20ms in Vite. Production builds also finish faster because Vite uses Rollup (which is faster than Webpack for bundling).

Ordered message parts — why tool cards render correctly

When Ima calls three tools and writes text between them, the naive approach (append text, append all tools at end) loses ordering. The parts[] approach preserves interleaving:

type ImaPart =
  | { type: 'text'; content: string }
  | { type: 'tool'; call: ImaToolCall; result?: string }

// Built as SSE chunks stream in:
// text-delta  → append to current text part (or create new text part)
// tool-call   → push new tool part (tool call JSON)
// tool-result → find matching tool part by id, set .result

// Result: text → tool → text → tool renders in the order they actually happened

SSE Streaming — How Text Appears as It's Generated

SSE vs WebSockets vs polling

Polling: client asks "any updates?" every N seconds. Wasteful, laggy. WebSockets: bidirectional persistent socket — great for chat apps where the client also sends events frequently. Requires an "upgrade" from HTTP. More complex to implement and proxy. SSE (Server-Sent Events): unidirectional server→client over a regular HTTP connection. The client opens one request; the server keeps writing chunks. Simpler than WebSockets, works over HTTP/1.1, automatic reconnection built into the browser's EventSource API. For Ima — we only need server→client streaming, so SSE is the right choice.

Server side (agent.py)

@router.post("/agents/stream")
async def stream(body: ChatRequest):
    return StreamingResponse(
        _ima_stream(body.messages, body.session_id),
        media_type="text/event-stream",
        headers={
            "Cache-Control": "no-cache",
            "X-Accel-Buffering": "no"  # tells Caddy/nginx not to buffer the stream
        },
    )

async def _ima_stream(messages, session_id):
    # Tool-use loop — can run many iterations
    while True:
        async for chunk in litellm.acompletion(stream=True, ...):
            if has_text:
                yield f'data: {{"type":"text-delta","payload":{{"text":"hello"}}}}\n\n'
            if has_tool_call:
                yield f'data: {{"type":"tool-call","payload":{{...}}}}\n\n'
        if no_tool_calls_this_round:
            break
        # execute tools, yield results, loop
    yield 'data: [DONE]\n\n'
    # The \n\n is the SSE event separator — the spec requires it

Client side (Shell.tsx)

const res = await fetch('/api/jobsearch/agents/stream', { method: 'POST', body: ... })
const reader = res.body!.getReader()
const decoder = new TextDecoder()

while (true) {
  const { done, value } = await reader.read()
  if (done) break
  const text = decoder.decode(value)
  // split on \n\n (SSE event boundaries)
  for (const event of text.split('\n\n')) {
    if (!event.startsWith('data: ')) continue
    const json = event.slice(6)
    if (json === '[DONE]') { /* finalize */ continue }
    const { type, payload } = JSON.parse(json)
    // dispatch to React state by type: text-delta, tool-call, tool-result
  }
}

X-Accel-Buffering: no. Caddy (and nginx) buffer responses by default — they accumulate data and send it in larger chunks for efficiency. For SSE this breaks the streaming experience: tokens would arrive in bursts. This header tells the proxy to forward each chunk immediately without buffering.

Interview talking points
  • SSE is HTTP/1.1 compatible — no upgrade handshake, works through standard proxies
  • The double newline \n\n is the SSE spec event delimiter — each logical event ends with it
  • Browser EventSource auto-reconnects; here we use raw fetch + ReadableStream for more control over how chunks are parsed
  • LiteLLM streams chunks as they arrive from DeepSeek — we forward each chunk immediately, so the user sees tokens appear in real-time rather than waiting for the full response

Docker + Compose

What Docker actually is

A container is a process with namespaced resources — its own filesystem, network interfaces, and process tree — isolated from the host. It's not a VM (no separate kernel), but it looks like one from inside. Docker packages an application with its exact dependencies (Python version, libraries, configs) into an image — a reproducible snapshot. Running the image creates a container. "Works on my machine" goes away because every environment runs the same image.

Multi-stage Dockerfile — why it matters

The build needs Node.js (to compile React). The runtime needs Python. If you use one stage, both Node and npm end up in the production image (~500MB bloat). Multi-stage build: Node compiles the React app, Python stage copies only the compiled output:

# Stage 1: compile React (Node.js needed, but not in final image)
FROM node:22-alpine AS frontend-builder
WORKDIR /app
COPY aios/frontend ./aios/frontend
RUN cd aios/frontend && npm install && npm run build
# output: aios/public/ (compiled JS + CSS bundles)

# Stage 2: Python runtime (Node never enters this image)
FROM python:3.12-slim AS runner
WORKDIR /app
RUN apt-get install -y git openssh-client \
    && git config --global --add safe.directory '*'
    # git needed: Ima runs git_commit_and_push from inside the container
COPY aios/requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY aios/ .
COPY --from=frontend-builder /app/aios/public ./public  # ← compiled React
EXPOSE 4116
CMD ["uvicorn", "main:app", "--host", "0.0.0.0", "--port", "4116"]

Caddy — Reverse Proxy

What a reverse proxy does

The browser connects to port 443 (HTTPS). Your FastAPI app runs on port 4116. A reverse proxy sits between them: it terminates the HTTPS connection (handles TLS), optionally enforces auth, then forwards the plain HTTP request to your app. Your app never needs to deal with TLS certificates. The proxy also handles multiple domains, rate limiting, and buffering.

Why Caddy over nginx?

Automatic TLS

Caddy automatically obtains and renews Let's Encrypt certificates. With nginx you'd need certbot as a separate cron job, with renewal hooks. Caddy just does it.

Simpler config

nginx configs are verbose — server blocks, location blocks, proxy_pass, ssl_certificate paths. Caddy's Caddyfile is 4 lines per domain. Same functionality, a tenth of the config surface area.

# caddy/Caddyfile — the entire proxy config
home.dmytropetryshchuk.com {
    basicauth { import /etc/caddy/auth_credentials }
    reverse_proxy localhost:4116
}

onekeyflow.com {
    basicauth { import /etc/caddy/auth_credentials }
    reverse_proxy localhost:4116
}

# TLS: automatic. Let's Encrypt cert obtained and renewed by Caddy.
# basicauth: HTTP Basic Auth — browser prompts for username + password.
#            Credential file on host (not in Docker) — never in repo.
# reload: sudo systemctl reload-or-restart caddy

Why Caddy runs on the host (not Docker). If Caddy were in Docker and the Docker daemon crashed or you ran docker compose down, you'd lose HTTPS access — including the ability to SSH and fix things via a browser-based terminal. Running Caddy as a host systemd service means it survives container restarts. The containers come and go; the proxy stays up.

Terraform describes infrastructure as declarative config files: "there should be a Hetzner CX22 server with these firewall rules and these DNS records." Run terraform apply and Terraform makes reality match the config, creating or updating as needed.

Webhooks — Fathom Meeting Flow

What a webhook is

A webhook is a server-to-server HTTP POST. Instead of your app polling Fathom's API every few minutes ("any new meetings?"), Fathom calls your server when something happens. Your server receives the event, processes it, and responds. This is event-driven integration: no polling, no delay, no wasted API calls.

HMAC-SHA256 signature verification

Anyone can send a POST to your webhook endpoint. To prove the request came from Fathom and not a random actor, Fathom signs the request body with a shared secret using HMAC-SHA256. Your server recomputes the signature and compares:

# routers/webhooks.py
import hmac, hashlib

def verify_fathom_signature(body: bytes, signature: str) -> bool:
    expected = hmac.new(
        FATHOM_WEBHOOK_SECRET.encode(),
        body,
        hashlib.sha256
    ).hexdigest()
    return hmac.compare_digest(expected, signature)
    # compare_digest: constant-time comparison prevents timing attacks

End-to-end: Fathom call → Ima can answer questions about it

1. Fathom records a meeting, finishes processing transcript 2. POST /webhooks/fathom {"event": "recording.completed", "recording": {"title": "Bram call", ...}} HMAC-SHA256 signature in Fathom-Signature header → verified 3. Handler creates os_events row → process_event.delay("fathom.received") Handler returns 200 immediately — Fathom doesn't wait 4. celery-worker runs fathom.run(payload) Builds markdown: title, date, attendees, summary, action items, transcript Writes to /vault/Meetings/2026-05-23 - Bram call.md 5. embed_document.delay("vault", path, content) OpenAI embedding → pgvector upsert (source_type="vault") Result: Ima can now answer "what did I discuss with Bram?" → semantic_search(query="Bram", source_type="vault") → finds the note → returns meeting summary, action items, transcript Key: use semantic_search(source_type="vault") NOT search_notes search_notes queries the SQL notes table — meetings aren't there

Self-Editing — Ima Modifying Her Own Codebase

Ima can read, edit, and commit source code — then push to git, triggering a CI/CD rebuild of herself. This is the most unusual part of the system.

The workflow

  • search_files(query, dir) — grep across the codebase to find the right file
  • read_code_file(path) — reads from /repo/aios/{path}
  • edit_code_file(path, old, new) — surgical string replacement (not full rewrites)
  • list_code_files(dir) — list files in a directory
  • run_shell(cmd) — run anything: git diff, npm run build, grep
  • git_commit_and_push(message, files) — commits staged files and pushes to both remotes
  • CI/CD picks up the push → Docker rebuild → rolling container restart (~2-4 min)

/app vs /repo — the critical distinction. The container has two "copies" of the code: /app is baked into the Docker image at build time. Editing /app/main.py changes an ephemeral container layer that vanishes on the next deploy. /repo is the live git checkout mounted as a bind volume — persists across container restarts and rebuilds. All self-edits must target /repo/aios/.

Mandatory auto-push. The system prompt (rule 12f) requires Ima to always commit and push after any code change — no session ends with uncommitted edits. For frontend changes, she runs npm run build first to confirm the build passes. This prevents leaving the codebase in a broken state between sessions.

Interview talking points — self-modifying AI systems
  • The safety mechanism here is the git history — every change is tracked, attributable, and revertable
  • CI/CD adds a second safety gate: if the Docker build fails (TypeScript error, missing import), the bad code never reaches production
  • Surgical edits (edit_code_file with old/new strings) are safer than full rewrites — smaller diffs, lower blast radius
  • The mandatory build step before push catches obvious breakage before it deploys
  • This pattern (LLM edits code → git push → CI/CD → auto-redeploy) is increasingly common in "autonomous engineering" workflows
