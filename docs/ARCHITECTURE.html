4. Database Architecture

The application uses two separate Postgres 16 databases (both inside the same Postgres container, initialized by postgres/init.sh) plus one SQLite file for OKF business data.

Why two Postgres databases?

The jobsearch and daily_log schemas have completely different concerns and independent migration histories. Keeping them in separate Alembic projects (alembic/ vs alembic_daily/) means a migration for the job search CRM cannot accidentally touch the habit tracker, and the connection pools are isolated so a long job-search query cannot starve a quick daily-log write.

jobsearch database

Holds all CRM data for the job search feature and the OS event queue.

5. The AI Agent (Ima / Jobby)

The agent lives in aios/agent.py and is a streaming tool-use loop over DeepSeek Chat via LiteLLM. It serves as a conversational CRM assistant that can read and write to the jobsearch database on the user's behalf.

Architecture: agentic loop with SSE streaming

POST /api/jobsearch/agents/stream
  Body: { messages: [{role, content}, ...] }
  Response: text/event-stream

Loop (in agent.py):
  1. Call litellm.acompletion(model="deepseek/deepseek-chat", stream=True, tools=TOOLS)
  2. Stream chunks:
     - text delta  -> yield SSE: {"type":"text-delta","payload":{"text":"..."}}
     - tool_calls  -> accumulate by index (streamed in fragments)
  3. If NO tool calls in response -> yield "data: [DONE]" and return
  4. If tool calls present:
     - append assistant message with tool_calls to context
     - for each tool call:
         yield SSE: {"type":"tool-call","payload":{toolCallId, toolName, args}}
         result = await run_tool(name, args, pool)
         yield SSE: {"type":"tool-result","payload":{toolCallId, result}}
     - append all tool results to context
     - loop back to step 1 (next LLM call with updated context)

SSE event types the frontend consumes

Event typePayloadFrontend action
text-delta{text: string}Append to message buffer, render as Markdown
tool-call{toolCallId, toolName, args}Show spinner with tool name
tool-result{toolCallId, result}Hide spinner, optionally show result
error{message: string}Show error message
[DONE]literal stringClose EventSource, finalize render

Agent system prompt design

Key behavioral rules baked into the system prompt (INSTRUCTIONS constant):

  • One question at a time -- drives a short interview before writing
  • Search before insert -- always call query_db or search_notes first to prevent duplicates
  • Restate before write -- summarizes the action and waits for confirmation
  • No fabrication -- asks rather than guessing emails, URLs, or names
  • Soft deletes -- uses status='dropped' not SQL DELETE; dropped leads are excluded from re-scrapes

Why these design choices?

  • DeepSeek over GPT-4: ~10x cheaper per token; performs comparably on structured JSON tool calls which is 95% of this use case
  • SSE over WebSockets: simpler server (one-directional streaming); FastAPI StreamingResponse with no extra library; works through Caddy with flush_interval -1
  • Tool-use loop over function calling once: the agent may need to search, then insert, then update in a single user turn -- multiple tool round-trips are required
  • LiteLLM over direct SDK: provider-agnostic; can switch to Claude or GPT-4 by changing one string in the model= argument

6. Event/Worker Pattern

All background work -- scraping, health checks, proposal generation, transcription -- flows through a single pattern: an os_events row is the unit of work.

Event flow

1
Trigger: UI button OR Celery Beat schedule fires run_scheduled(event_type)
2
os_events row inserted with status='pending', source='ui' or 'schedule'
3
process_event.delay(event_id) enqueues task to Redis
4
Celery worker picks it up: sets status='processing', started_at=now(), commits
5
Worker dispatches to handler by event.type (e.g. "scrape.sd" -> jobspy_scraper.run)
6
On success: status='done', result stored in payload.result
7
On failure: status='failed', error=str(exc)

Beat schedule

Event handlers registry

Handlers are imported lazily inside _import_handlers() to avoid circular import issues at module load time. The mapping is a simple dict[str, Callable]: 

"health.check"         -> workers.health.run
"scrape.sd"            -> workers.scrapers.jobspy_scraper.run
"scrape.yc"            -> workers.scrapers.yc.run
"scrape.hn"            -> workers.scrapers.hn.run
"fathom.received"      -> workers.scrapers.fathom.run
"whisper.transcribe"   -> workers.scrapers.whisper_transcribe.run
"supadata.transcript"  -> workers.scrapers.supadata_transcript.run
"local_events.pull"    -> workers.scrapers.local_events.run

Two Celery queues

The worker runs two queues: celery (default, all scraper/health tasks) and okf (proposal generation). Separating them means a long-running proposal LLM call cannot block the job scraper queue.

7. Job Search Pipeline

Scraper architecture (jobspy_scraper.py)

Uses python-jobspy to query Indeed and LinkedIn simultaneously. The scraper runs a cartesian product of search_terms x locations x sites, so with 5 terms and 3 locations that is 30 API calls per scrape run (15 Indeed + 15 LinkedIn).

Deduplication

  • In-memory dedup within a single scrape run via a set of company::title keys
  • DB-level dedup via upsert_job_posting: inserts only if no row matches (company_id, lower(title))
  • Dropped leads (status='dropped') are preserved in DB but never shown in the leads feed -- the scraper checks for existing rows before inserting so dropped jobs stay dropped across future scrape runs

Filtering layers

  1. skip_titles: case-insensitive substring match against a configurable list (intern, director, VP, etc.)
  2. is_defense filter: utility in utils.py -- skips defense/government contractors by company and title keywords
  3. area_keywords filter: the job location string must contain at least one area keyword (San Diego, Carlsbad, remote, etc.)
Live config tuning: the scraper reads its config from the scraper_settings table at runtime. The AI agent exposes get_scraper_settings and update_scraper_settings tools, so the user can tell the agent "stop showing me senior roles" and it edits the skip_titles array in the DB -- no code changes, no redeploy.

Contact pipeline stages

Job lead discovered (status='new')
        |
        v
  User applies (status='applied') -- or drops (status='dropped')
        |
        v
  Contact created: stage = Outreached
        |
        v (they reply)
  stage = Responded
        |
        v (call / interview)
  stage = Ongoing
        |
        v (goes cold / rejected)
  stage = Dead

The retro page (GET /api/jobsearch/retro) aggregates this funnel data: outreach rate, response rate, avg days to response, contacts needing follow-up (no interaction in 7+ days), and weekly/daily interaction counts.

8. CI/CD Pipeline

Two jobs, paths-filtered

The .github/workflows/deploy.yml workflow has two independent jobs that only run when relevant files change:

JobTriggers onWhat it does
deploy-app aios/** file changes Build + push Docker image to GHCR, then deploy to VPS
deploy-infra docker-compose.yml or caddy/** changes SSH to VPS: git pull + compose up + reload Caddy

deploy-app step by step

1
git push master triggers the workflow
2
dorny/paths-filter checks if any aios/** file changed; skips if not
3
Login to GHCR using GITHUB_TOKEN (no separate secret needed)
4
docker buildx build -- multi-stage: Node 22 alpine builds frontend, Python 3.12-slim runs backend
5
Image pushed to ghcr.io/dpetryshchuk/ai-os/aios:latest with GHA layer cache
6
SSH to VPS via appleboy/ssh-action using VPS_SSH_KEY secret
7
git fetch && git reset --hard origin/master (syncs compose file)
8
docker compose pull aios -- pulls the new image from GHCR
9
docker compose up -d aios celery-worker celery-beat -- rolling restart of app containers only; postgres and redis are untouched

Why GHCR?

  • Free for public and private repos under GitHub's included storage
  • Authentication uses the same GITHUB_TOKEN that is automatically injected into every Actions run -- no extra secret to manage for the registry
  • Tight integration: package is linked to the repository in the GitHub UI

Why no auto-migration?

Database migrations are a manual step run via docker compose exec aios alembic upgrade head after deploy. This is a deliberate safety gate: an Alembic migration that drops a column or renames a table cannot be rolled back automatically. Running it manually gives one final chance to verify the migration SQL before it runs against production data.

terraform import vs terraform apply

The VPS was provisioned before Terraform was added to the project. Running terraform apply on an already-running server would try to create a second server. The correct workflow is: 

# Import the existing server into Terraform state
terraform import hcloud_server.vps <server_id>
terraform import hcloud_firewall.public <firewall_id>
terraform import hcloud_ssh_key.operator <ssh_key_id>

# After import, plan should show no changes (drift check)
terraform plan

# Future changes (resize, new DNS record) are applied normally
terraform apply

The prevent_destroy = true lifecycle rule on hcloud_server.vps ensures terraform destroy will refuse to delete the VPS without first removing that block from the config.

10. Multi-Tenant Architecture

The same single binary serves two distinct audiences on two different domains, with different branding and navigation.

How it works

ThemeLight modeDark mode
NavPersonal nav itemsBusiness nav items
DetectionClient-side: window.location.hostname in Shell.tsx
Caddy configBoth domains reverse_proxy localhost:4116 -- identical backend
AuthSame HTTP Basic Auth credentials on both domains

Why not separate deployments?

One developer, one VPS. A second deployment would require a second port, second Docker service, second set of CI/CD jobs, and second DB connection config -- all for the same codebase. Domain-switching at the frontend layer costs essentially nothing and keeps the operational surface minimal.

11. OKF Business Tools

OneKeyFlow (OKF) is the business side of the app. It lives on os.onekeyflow.com and provides two tools: proposal generation and a revenue P&L tracker.

Proposal generation pipeline

1
User fills in a discovery form (client name, business description, problem, solution, tools, timeline, price)
2
POST /api/proposals/generate enqueues generate_proposal.apply_async(..., queue='okf')
3
Celery worker (okf queue) calls _call_proposal_llm: DeepSeek with response_format=json_object + few-shot examples from prompts/proposal.json
4
LLM returns structured JSON: sections, pricing, timeline, scope
5
pandadoc.build_payload maps the JSON to a PandaDoc API payload
6
pandadoc.create_document sends to PandaDoc API; returns doc_id
7
pandadoc.wait_for_draft polls the API until document status is draft (ready to review)
8
Result stored in okf_db.events table; frontend polls GET /api/proposals/status/{job_id} until done

Revenue P&L tracker

A simple monthly P&L table stored in SQLite. The _enrich function in okf_db.py computes derived fields at read time (net revenue, operating profit, tax provision, net profit, net margin) rather than storing them, keeping the stored data minimal and the calculations auditable.

okf_db.py pattern

A thin module that wraps sqlite3 directly -- no ORM. Each function opens and closes its own connection. This is safe because SQLite operations here are always short-lived and never concurrent. The same event lifecycle pattern (create_event / start_event / complete_event / fail_event) mirrors the Postgres os_events pattern used by the main app.

12. Langfuse Integration

Langfuse is an open-source LLM observability platform. It provides traces, spans, cost tracking, token counts, latency histograms, and user feedback scores -- essentially a "Datadog for LLM calls."

Current state

The infrastructure is already wired up: config.py exposes langfuse_public_key and langfuse_secret_key as env vars, and docker-compose.yml passes them into the aios and celery-worker containers. LiteLLM has native Langfuse support -- enabling it requires one line of code.

To enable (LiteLLM native callback)

# In agent.py, after imports:
import litellm
litellm.success_callback = ["langfuse"]

# Or set via env var (no code change at all):
LANGFUSE_PUBLIC_KEY=pk-lf-...
LANGFUSE_SECRET_KEY=sk-lf-...
# LiteLLM auto-enables Langfuse when both keys are present

Cloud vs self-hosted

Langfuse Cloud (langfuse.com)Self-hosted (Docker)
SetupSign up, get keys, set env varsAdd Langfuse + Postgres service to docker-compose.yml
CostFree tier (50k observations/month)Extra ~200 MB RAM on VPS; free otherwise

What you get

  • Per-trace cost breakdown (input tokens, output tokens, DeepSeek pricing)
  • Tool call inspection: see exactly which tools the agent called, with args and results
  • Latency per LLM call and per tool execution
  • Session grouping (one conversation = one trace with N spans)
  • Scores: you can attach thumbs-up/down feedback from the UI to traces

13. Design Decisions

Web framework FastAPI Django, Flask, Express Async-native (asyncpg works natively); Pydantic validation; auto OpenAPI docs; significantly faster than WSGI frameworks under concurrent load

Async DB driver asyncpg psycopg3 async, SQLAlchemy async asyncpg is the fastest Postgres async driver for Python; direct SQL gives full control and avoids ORM overhead for read-heavy API endpoints
Streaming protocol Server-Sent Events (SSE) WebSockets, long-polling SSE is unidirectional (server to client) which is all the agent stream needs; simpler than WebSockets (no upgrade handshake, works through HTTP/1.1); native browser EventSource API
