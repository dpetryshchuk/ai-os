AI OS Architecture

A personal command center — job search CRM, AI assistant, knowledge base, finances, and business OS — deployed as a single FastAPI monorepo on a $4.50/mo Hetzner VPS.

Big Picture

One Docker image. Two domains. One FastAPI app handling everything from the database to the AI agent to the React SPA.

User's browser │ HTTPS Caddy (reverse proxy, basicauth, TLS — runs as host systemd service) │ FastAPI :4116 ← serves both domains from the same port ├── /api/* → Python route handlers ├── /webhooks/* → Fathom, etc. └── /* → React SPA (index.html) FastAPI talks to: Postgres (pgvector:pg16) — two databases: jobsearch + daily_log Redis — Celery broker + result backend SQLite — okf.db (proposals) + sessions.db (chat history) Background tasks: celery-worker — scrapers, embeddings, proposal generation celery-beat — cron scheduler (8am scrapes, Sunday backfill) External APIs: DeepSeek — Ima's LLM (cheap, fast, tool-use capable) OpenAI — text-embedding-3-small for semantic search Langfuse — LLM observability (trace every Ima conversation) PandaDoc — proposal PDF generation Fathom — meeting recordings (webhooks → vault notes)

One repo, two personalities. home.dmytropetryshchuk.com = personal light theme. onekeyflow.com = agency dark theme. The distinction is made in the browser: IS_OKF = hostname.includes('onekeyflow') applies the dark class to <html>. Both domains share the same backend, database, and Ima instance.

Request Lifecycle

What happens when a user clicks "Add company" in the job search CRM:

1. Browser sends POST /api/jobsearch/companies 2. Caddy checks basicauth, strips TLS, forwards to localhost:4116 3. FastAPI matches route in routers/jobsearch.py Injects dependency: pool = Depends(db.get_jobsearch_pool) 4. Handler calls await pool.execute("INSERT INTO companies ...") asyncpg sends SQL over a persistent pooled TCP connection to Postgres No ORM. Raw SQL. Fast. Parameterized ($1) — no SQL injection possible. 5. Returns {"ok": True, "id": "abc123"} — Pydantic validates, FastAPI serializes

What happens when a user triggers a job scrape:

1. Browser sends POST /api/jobsearch/trigger/scrape.sd 2. Handler validates task_type in allowed set Inserts row into os_events table (status = "pending") 3. Calls process_event.delay(event_id) Celery serializes args to JSON → pushes to Redis queue Handler returns immediately — non-blocking 4. celery-worker (separate container) picks up task from Redis Loads event from Postgres, marks it processing 5. Runs sd_run(payload, session) Scraper fetches jobs, upserts into job_postings Marks event done

FastAPI App

FastAPI is an async Python web framework. It reads type hints to auto-generate validation and OpenAPI docs. Every route is an async function — it never blocks a thread while waiting for the database.

Entry point: aios/main.py

The app has a lifespan — code that runs once on startup and once on shutdown. This is where connection pools are initialized:

main.py@asynccontextmanager
async def lifespan(app: FastAPI):
    _configure_litellm()         # wire Langfuse callbacks
    await db.init_jobsearch_pool()   # create asyncpg pools (warm connections)
    await db.init_daily_log_pool()
    yield                        # app runs here, serving requests
    await db.close_jobsearch_pool()  # clean shutdown
    await db.close_daily_log_pool()

Dependency Injection

FastAPI's Depends() injects the database pool into route handlers. No global state accessed directly in handlers — testable and clean:

@router.post("/companies")
async def create_company(
    body: CompanyCreate,
    pool: asyncpg.Pool = Depends(db.get_jobsearch_pool)  # injected per request
):
    await pool.execute("INSERT INTO companies ...")
    return {"ok": True}

The pool is created once at startup. get_jobsearch_pool() returns the module-level pool reference — calling it is free, creating connections is not (but the pool keeps them warm).

SPA fallback

The last route is a catch-all that serves index.html for every non-API path. This lets React Router handle navigation client-side — you can deep-link to any page and the server always returns the SPA:

@app.get("/{full_path:path}")
async def spa(full_path: str) -> FileResponse:
    candidate = _PUBLIC / full_path
    if candidate.is_file():
        return FileResponse(candidate)   # serve asset directly
    return FileResponse(_PUBLIC / "index.html")  # else: SPA

Database Layer

Two Postgres databases

Job search data and daily log data live in separate databases. This isolates concerns — the jobsearch DB can hold vectors and grow large without affecting habit tracking data.

What is a connection pool?

Opening a database connection is slow — TCP handshake, TLS, Postgres authentication. A pool maintains N pre-opened connections and loans them out per request:

# db.py — pool created once at startup
_jobsearch_pool = await asyncpg.create_pool(settings.jobsearch_database_url)
# Default: min 10 connections ready to go

# In any handler — gets a connection from the pool instantly
row = await pool.fetchrow("SELECT * FROM companies WHERE id = $1", id)
# Connection returned to pool when done

Two connection flavors. FastAPI routes use asyncpg (async, no ORM). Celery workers use psycopg2 (sync, plain SQL) — Celery tasks run in their own processes and can't use async code. The SyncSession in db.py wraps SQLAlchemy for the os_events model used by Celery.

pgvector extension

The jobsearch database has the vector PostgreSQL extension. This adds a vector(1536) column type and an ivfflat index for approximate nearest-neighbor search:

-- Created in postgres/init.sh (runs once when Postgres container first starts)
CREATE EXTENSION IF NOT EXISTS vector;

-- embeddings table (migration 0008_add_pgvector)
CREATE TABLE embeddings (
    id          text PRIMARY KEY,
    source_type text,           -- 'note', 'job_posting', 'vault'
    source_id   text,           -- the ID or path of the source document
    chunk_text  text,           -- first 4000 chars (for display)
    embedding   vector(1536),   -- OpenAI text-embedding-3-small output
    UNIQUE (source_type, source_id)
);

CREATE INDEX ON embeddings USING ivfflat (embedding vector_cosine_ops);

Celery Workers

Celery is a distributed task queue. Tasks that are slow, periodic, or shouldn't block an HTTP response are offloaded here. Celery workers run as separate containers from the FastAPI app.

How it works

FastAPI handler calls process_event.delay(event_id) → serializes to JSON → pushes to Redis queue → returns immediately celery-worker (separate container, same image) → polls Redis → picks up task → runs process_event(event_id) → loads os_events row from Postgres → marks "processing" → dispatches to handler by event.type → marks "done" or "failed" celery-beat (separate container) → reads beat_schedule → creates os_events rows on cron → enqueues

The event audit trail

All background work flows through the os_events table. You can see exactly what ran, when, how long it took, and any error message:

-- Every trigger creates a row
INSERT INTO os_events (id, source, type, payload, status)
-- Status lifecycle:
pending → processing → done
                    → failed (error column filled)

Two queues

The worker listens on celery (default — scrapers, embeds) and okf (proposal generation). OKF tasks are isolated so a slow proposal LLM call can't block job scrapes.

Lazy handler imports

Worker modules are imported inside _import_handlers(), not at module load. This prevents import-time circular dependencies and keeps the Celery app lightweight at startup:

def _import_handlers() -> dict:
    from workers.scrapers.fathom import run as fathom_run
    from workers.scrapers.jobspy_scraper import run as sd_run
    # ...
    return {
        "fathom.received": fathom_run,
        "scrape.sd": sd_run,
        "embed.backfill": lambda payload, session: embed_backfill(),
        "embed.vault": lambda payload, session: embed_vault(),
    }

Ima — The AI Agent

Ima is an agentic AI assistant that can use tools, run shell commands, edit the codebase, and query your data. She lives in aios/agent.py and is accessed through the persistent top-bar chat panel.

The tool-use loop

A standard LLM call takes a prompt and returns text. An agent takes a message and can call tools repeatedly until the task is done:

User: "find me senior eng jobs at AI startups" Iteration 1: LLM decides: call semantic_search(query="senior engineer AI startup") Tool runs → returns 5 matching jobs Result appended to message history Iteration 2: LLM decides: call search_jobs(filters={stage: "active"}) Tool runs → returns 10 more Result appended Iteration 3: LLM has enough context → returns final response text Loop exits → response streamed to browser

System prompt loading

Every request to Ima starts by loading _load_instructions() which assembles the system prompt from three sources:

def _load_instructions() -> str:

    # Appended if they exist:
    # /app/data/memory/USER.md  → who Dima is, preferences

Self-editing: how Ima modifies the codebase

The VPS mounts the live git repo into the container: /home/dima/writing → /repo. Ima's file tools operate on /repo/aios/ — the actual source files on disk.

Not /app. The container also has /app/ — a copy of the code baked into the Docker image at build time. Editing /app/ changes an ephemeral layer that vanishes on the next deploy. All self-edits must target /repo/aios/. After editing, git_commit_and_push triggers CI/CD → Docker rebuild → auto-redeploy.

Job lead lifecycle

Job leads flow through statuses: new → applied / dropped. Dropping a lead sets status='dropped' — the record is never deleted, just hidden from main views. This preserves history for retrospectives. The Leads page has a Trash2 button that calls update_lead_status(status='dropped').

LiteLLM + Langfuse

LiteLLM

LiteLLM is a unified interface for 100+ LLM providers. Instead of writing provider-specific code, you call litellm.acompletion(model="deepseek/deepseek-chat", ...) and LiteLLM handles the translation. Swapping models is a one-line change.

# agent.py — streaming tool-use call
response = await litellm.acompletion(
    model="deepseek/deepseek-chat",   # cheap, fast, tool-use capable
    messages=messages,                 # full history + system prompt
    tools=TOOLS,                       # JSON schema of all tools
    stream=True,                       # SSE streaming
)
async for chunk in response:
    # process: text-delta, tool-call, tool-result

Why DeepSeek?

DeepSeek is ~10-20× cheaper than GPT-4 for the same quality on tool-use tasks. It speaks the OpenAI tool-use protocol (same JSON schema), so switching models is trivial.

Langfuse

Langfuse traces every LiteLLM call — prompt, response, tools called, latency, token counts. One-time setup in main.py — no code changes needed in routes:

litellm.success_callback = ["langfuse"]
litellm.failure_callback = ["langfuse"]

Version pinning. Langfuse 3.x+ moved to an OpenTelemetry-based API and removed Langfuse().trace(). LiteLLM 1.89.3 requires that method. Pin: langfuse==2.60.10 — the last release with the old low-level SDK. No Dockerfile patches needed with this pin.

pgvector + Semantic Search (RAG)

Keyword search finds documents containing a word. Semantic search finds documents that mean the same thing — "senior engineer AI startup" can surface a job posting titled "founding ML infrastructure engineer."

How embeddings work

An embedding is a list of 1536 numbers representing a text's meaning. Similar meanings produce similar number lists. Cosine distance between two vectors measures how similar their meanings are.

Text: "founding engineer AI startup" ↓ OpenAI text-embedding-3-small (~$0.02 / million tokens) Vector: [0.021, -0.048, 0.103, ... 1536 floats] ↓ stored in Postgres via pgvector Query: "senior ML engineer" ↓ same embedding process → query vector ↓ SELECT ... ORDER BY embedding <=> $1 LIMIT 10 (<=> = cosine distance, lower = more similar) Results ranked by semantic similarity

SSE Streaming

Server-Sent Events let the server push data to the browser over a long-lived HTTP connection. Unlike WebSockets, SSE is one-way (server → browser) and works over plain HTTP — no upgrade protocol needed.

Server side (agent.py)

@router.post("/agents/stream")
async def stream(body: ChatRequest):
    return StreamingResponse(
        _ima_stream(body.messages),
        media_type="text/event-stream",
        headers={"Cache-Control": "no-cache", "X-Accel-Buffering": "no"},
    )

async def _ima_stream(messages):
    # Tool-use loop — each iteration may yield tool-call + tool-result events
    while True:
        async for chunk in litellm.acompletion(stream=True, ...):
            if chunk has text:
                yield f'data: {{"type":"text-delta","payload":{{"text":...}}}}\n\n'
            if chunk has tool_call:
                yield f'data: {{"type":"tool-call","payload":{{...}}}}\n\n'
        if no more tool calls:
            break
        # run tools, yield results, loop back
    yield 'data: [DONE]\n\n'

Client side (Shell.tsx)

const reader = res.body!.getReader()
while (true) {
  const { done, value } = await reader.read()
  if (done) break
  // split on \n\n (SSE event separator)
  // parse each JSON chunk
  // update React state → re-render
}

The \n\n double newline is the SSE spec — it marks the end of one event. The browser splits the stream on this and processes each chunk.

Webhooks — Fathom Meeting Flow

Fathom records a meeting ↓ POST /webhooks/fathom HMAC-SHA256 signature in Fathom-Signature header Verified against FATHOM_WEBHOOK_SECRET ↓ os_events row created → process_event.delay() ↓ celery-worker runs fathom.run(payload) Builds markdown: title, date, attendees, summary, action items, transcript ↓ Writes to /vault/Meetings/YYYY-MM-DD - Title.md ↓ embed_document.delay("vault", path, content) OpenAI embedding → pgvector upsert Result: Ima can now find this meeting via semantic_search "what did I discuss with Bram?" → surfaces the vault note Note: search_notes only queries the notes DB table. Fathom meetings are vault files — Ima must use semantic_search(source_type="vault") to find them.

  • search_files(query, dir) grep-style search across the codebase
  • run_shell(cmd) can run anything: git diff, grep, npm run build
  • git_commit_and_push(message, files) commits and pushes to both remotes
  • CI/CD picks up the push → Docker rebuild → rolling container restart (~2 min)

The rule: always use /repo/aios/. The /app/ directory is baked into the Docker image at build time. Edits there disappear on the next deploy. Only /repo/ is the persistent git checkout that survives container recreation.
